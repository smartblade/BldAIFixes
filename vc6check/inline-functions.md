# Inline functions in Visual C++ 6.0

How `cl.exe` of Visual C++ 6.0 with `/Ob1` compiles inline functions and
how they are found in the original binaries. Rules of placing local
variables in the stack frame are described in
[stack-layout.md](stack-layout.md).

With `/Ob1` Visual C++ 6.0 expands inline functions (defined in a class or
declared `inline`) at their calls. A separate copy of an inline function
is compiled into a COMDAT section only if something refers to it:

- its address is taken: `&B::Twice` makes `?Twice@B@@QBENXZ`, without it
  there is no code of `B::Twice` in the object file;
- it is virtual: the table of virtual methods refers to it, so inline
  virtual methods have addresses (`B_Surface::GetPolygon` at `0x0045BCB0`,
  `B_3DRasterDevice::WriteText` at `0x1002B8F0`);
- it can't be expanded (recursion, the limit of the depth of nested
  expansions).

A virtual destructor is an exception: the table refers to the scalar or
vector deleting destructor generated by the compiler (`??_G`, `??_E`),
which expands the inline destructor. So `~B_OctantNodeBase` has no
address, `0x00453AC0` is `??_GB_OctantNodeBase@@UAEPAXI@Z`. The linker
removes COMDAT sections nobody refers to (`/OPT:REF`).

An inline function expanded at all its calls has no address in the binary
and can't be marked with an entry point. Its code is repeated at each call,
so it is restored from the repeated code: the default constructor of
`B_Vector` (three zero `double` fields), the constructor and the destructor
of `B_OctantNodeBase`, the constructor of `B_PtrArray` with its initializer
list, `B_PtrArray::Append` and `B_PtrArray::Clear`, `B_Plane::Distance`.

Constructors of elements of arrays created by `new T[n]` are expanded in
the loop of the construction too: a loop calling a constructor (e.g.
`0x00449B20` called at `0x004458E7`, `0x0044608C` and `0x00446580`)
means that the constructor is not inline, it is defined out of the class.

## Limits of expansion

Not every call of an inline function is expanded. `check_inline_limit.py`
compiles procedures calling inline methods of the same size (`Big*`, a few
statements) and prints the calls left in the listing:

```
Sequence15: 4 calls left: Big7 Big7 Big7 Big7
Sequence30: 19 calls left: Big7 Big7 Big7 ...
SmallFirst: 1 calls left: Big7
Nested: 3 calls left: Big2 Big3 Big4
```

- A procedure has a limit of the expanded code: the calls are expanded in
  the order of the source until the limit (11 calls of `Big7`), the rest
  stay calls of a COMDAT copy. Calls of small functions (returning a
  field) hardly count: 20 of them before 12 calls of `Big7` leave only
  the last `Big7`.
- The calls of the procedure are expanded first, the calls inside the
  expanded functions after them (`F1` and `G` are expanded before their
  callees).
- An expanded inline function has its own limit for the calls in it,
  including the deeper ones: one `Big*` fits into `F1`, the second one
  doesn't; `G` expands `F2` and `Big5`, but not `Big3` and `Big4` of `F2`.
  A call that doesn't fit is left, a later smaller call can still be
  expanded.

So a call of a COMDAT copy of an inline function in the original binary
means that the call didn't fit: either the procedure has expanded too
much before it, or the call is inside another inline function. `Blade.exe`
has 29 copies of `B_PtrArray<T>::Append` called from many procedures,
while `SetDefaultMass` and `AddCombustionDataFor` expand it.
`CreateTriggerSector` (`0x0042B97A`) calls the copy at `0x0042C640`: the
call is in inline `AddTriggerSector(sector, name)` (with `assert(name)`
and an expanded `B_PtrArray::Find` before it), which is called from inline
`AddTriggerSector(sector)` with `assert(sector)`. Without these functions
(the master version of BldMystery), or with `assert(sector)` moved to
`CreateTriggerSector` and only `AddTriggerSector(sector, name)` inline, it
is expanded. One inline function with both asserts, `Find` and `Append`
leaves the call too, but places `name` before the temporaries of `Find`
(see [stack-layout.md](stack-layout.md)). The limits also depend on the
callees: an extra empty inline destructor of `B_Vector` changes the
constructors of `array_t<B_Vector>` and makes the constructor of
`B_PtrArray<void>` a call.

## Inline constructors and vtables

- The vtable is stored after the initializer list and before the body of
  a constructor. A constructor assigning the fields in its body stores
  the vtable first. The original `B_PtrArray` and `array_t` constructors
  initialize the fields in the initializer list (the vtable is stored
  last).
- A parameter of another type than the field (`unsigned int increment`
  for an `int` field) is copied to a temporary at an expanded call with
  the default argument; with the same type the constant is stored
  directly.
- The expanded constructor stores the vtable of each class of the
  hierarchy: three stores in a row (`0x005BD914`, `0x005BD910`,
  `0x005BD90C` for `B_App::afterFrameFuncs`) mean three classes. The
  destructor generated by the compiler (no destructor in the class)
  doesn't store the vtable, so the scalar deleting destructors of the
  derived classes store only the vtable of the base class with the
  destructor (`~B_PtrArray`). In BldMystery the levels are
  `B_PtrArray2<T>` and `B_PtrArray3<T>` (original names unknown),
  `B_NDataBase<T>` is the fourth level (`B_csvs` stores four vtables).
- Each vtable with only a scalar deleting destructor has one entry. A
  class without a virtual destructor has no deleting destructor in its
  vtable: the vtable of `B_ConfigSection` (rOpenGL) has three methods
  returning 0, and destroying a `B_VideoModeSection` doesn't store it.
- An implicit constructor of a class imported from a DLL
  (`struct __declspec(dllimport) B_ElementCSV`) stores the imported vtable
  (`__imp_??_7B_ElementCSV@@6B@`) and then the local vtable (`??_S`).
  `Blade.exe` stores only its own vtable of `B_ElementCSV`, and
  `BBLibc.dll` exports only `??1B_ElementCSV@@UAE@XZ`: only the destructor
  is imported.

## Other signs of inline functions

- A comparison stored with `setne`/`sete` and tested later is a `bool`
  (or `int`) result of an inline function or a `bool` variable:
  `bool found = Find(name) != NULL;`. A condition written in the `if`
  jumps directly.
- `setne` followed by `test` of the whole register, without storing, is
  the result of an inline function used in a condition: `int HasData()
  { return data != NULL; }` of `B_ProcTexture` in `UpdateAGTexture`
  matches it.
- An inline function returning a field copies it to a temporary
  (`B_AGTexture::BmpHandle`), a direct access compares the field.
- An inline function returning the found element ends the search with a
  jump past the code storing `NULL`, like `goto` in the decompiled code.
  The temporaries of the search (the `B_Name` converted from
  `const char *`, `i`, the result) are destroyed right after the
  expression calling it.
