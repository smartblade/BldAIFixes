# Stack layout of local variables in Visual C++ 6.0

Rules of placing local variables in the stack frame by `cl.exe` of
Visual C++ 6.0 without optimizations (`/Od`). They are derived from test
sources compiled with `cl.exe` 12.00.8804 (Visual C++ 6.0 SP5/SP6) and
checked on BldMystery sources.

## Rules

1. The order of declarations inside one block doesn't matter:
   `int a; int b; int c;` and `int c; int b; int a;` give the same offsets.
2. Blocks are placed in preorder. All variables of the body of the
   procedure are placed first, including variables declared after nested
   blocks, then the nested blocks in the order of the source, each block
   followed by its own nested blocks. A variable declared in the
   initialization of `for` belongs to the enclosing block. Sibling blocks
   don't share stack memory.
3. Inside a block variables are ordered by the hash of their names: hash
   buckets are placed in ascending order, a variable declared later is
   placed first inside a bucket. There are 16 buckets:

   ```python
   def bucket(name):
       v = 0
       for ch in name:
           v = ((v << 2) + (v >> 4) + ord(ch)) & 0xFFFFFFFF
       return (v ^ (v >> 16)) & 15
   ```

4. Each variable is placed at the next lower address, its size is rounded
   up to 4 bytes. `double` variables are not aligned to 8 bytes.
5. Variables that are never used get no stack memory.
6. `this` saved in the stack frame is placed after all local variables.
   Temporaries of the compiler (`$T` in listings) and local variables of
   inlined procedures are placed after the variables of the source.

Example of rules 2 and 3 (offsets of the listing in the comments):

```cpp
void f()
{
    int a;              // -4,  bucket 1
    {
        int b;          // -12, nested block
        double d;       // -20, nested block
        use(&b);
        use(&d);
    }
    int c;              // -8,  body of the procedure, bucket 3
    use(&a);
    use(&c);
}
```

## Consequences for recompiled code

The offsets of the original binary restrict the declarations:

- A variable placed above a variable of the body of the procedure is
  declared in the body too, even if it is used only in a nested block. In
  `B_OctTreeSectorsList::BuildSurfaceCache` (`0x0045327B`) `distance`
  (`-8`) is above `i` (`-12`), so it is declared at the start of the
  procedure, not inside the loop where it is used.
- The names of the variables of one block must have buckets in the order
  of their offsets, a name with a wrong bucket changes the layout. For
  example `current_surface` (bucket 8) is placed below `distance`
  (bucket 2) of the same block, although it is declared earlier.
- Variables of one block in the same bucket are declared in the reverse
  order of their offsets.

## Checks

- The hash function is derived from the order of 1466 names and checked on
  600 random names of 1 to 31 characters (letters, digits and `_`), all
  buckets match.
- All sources of `Blade.exe` (49 files), `BBLibc.dll` (21 files) and
  `rOpenGL.dll` (9 files) of BldMystery are compiled (in `App.cpp` and
  `WinClock.cpp` constructions not supported by Visual C++ 6.0 are
  replaced), the order of the local variables in the listings (`/FAs`) is
  compared with the rules. Of 113 procedures with two or more local
  variables 100 are checked by `check_stack_layout.py` and all of them
  match, including `operator >>` of `B_World` with 13 variables in
  8 nested blocks, variables of the same names in different blocks and
  variables of inlined procedures. `B_3DRasterDevice::WriteText` defined in
  `RasterDevice.h` matches too. The rest are methods of templates and
  procedures with variables of inlined procedures only.
- `BuildSurfaceCache` with `distance` declared in the body of the
  procedure has the same stack frame as in `Blade.exe` (built with
  12.00.8799), so the rules are the same for both builds at least in this
  case.

## Inline functions

With `/Ob1` Visual C++ 6.0 expands inline functions (defined in a class or
declared `inline`) at their calls. A separate copy of an inline function
is compiled into a COMDAT section only if something refers to it:

- its address is taken: `&B::Twice` makes `?Twice@B@@QBENXZ`, without it
  there is no code of `B::Twice` in the object file;
- it is virtual: the table of virtual methods refers to it, so inline
  virtual methods have addresses (`B_Surface::GetPolygon` at `0x0045BCB0`,
  `B_3DRasterDevice::WriteText` at `0x1002B8F0`);
- it can't be expanded (recursion, the limit of the depth of nested
  expansions).

A virtual destructor is an exception: the table refers to the scalar or
vector deleting destructor generated by the compiler (`??_G`, `??_E`),
which expands the inline destructor. So `~B_OctantNodeBase` has no
address, `0x00453AC0` is `??_GB_OctantNodeBase@@UAEPAXI@Z`. The linker
removes COMDAT sections nobody refers to (`/OPT:REF`).

An inline function expanded at all its calls has no address in the binary
and can't be marked with an entry point. Its code is repeated at each call,
so it is restored from the repeated code: the default constructor of
`B_Vector` (three zero `double` fields), the constructor and the destructor
of `B_OctantNodeBase`, the constructor of `B_PtrArray` with its initializer
list, `B_PtrArray::Append` and `B_PtrArray::Clear`, `B_Plane::Distance`.

Constructors of elements of arrays created by `new T[n]` are expanded in
the loop of the construction too: a loop calling a constructor (e.g.
`0x00449B20` called at `0x004458E7`, `0x0044608C` and `0x00446580`)
means that the constructor is not inline, it is defined out of the class.

## Scripts

- `stack_layout.py`: the hash of names (`bucket`) and the key of the order
  of variables in the stack frame (`order_key`).
- `check_hash.py`: compiles procedures with variables of random (or given)
  names and compares the buckets found from the listing with
  `stack_layout.bucket`.
- `check_stack_layout.py`: checks the rules on listings of compiled
  sources: local variables of each procedure sorted by `order_key` must
  have decreasing offsets. Blocks and declarations are found in the
  source by a simple parser, procedures it can't handle are skipped.

`cl.exe` is run as the command in the `VC6_CL` environment variable (`cl`
by default). On Linux it can be run with Wine:

```sh
export WINEPATH="Z:$VC6/VC98/Bin;Z:$VC6/Common/MSDev98/Bin"
export VC6_CL="wine CL.EXE"
python3 vc6check/check_hash.py
python3 vc6check/check_hash.py distance current_surface i
```

Listings for `check_stack_layout.py` are made with `/FAs`, a listing
`Name.asm` is checked with `Name.cpp` of the sources directory (or
`Dir_Name.asm` with `Dir/Name.cpp`):

```bat
set CFLAGS=/Zp4 /MD /Od /Ob1 /Gd /W3 /FAs /Falistings\
vc6check\build.bat C:\path\to\BldMystery
python vc6check\check_stack_layout.py listings C:\path\to\BldMystery\src\BBLibc
```
