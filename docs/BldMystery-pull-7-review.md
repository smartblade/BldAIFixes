# Review of BldMystery pull request 7

Pull request: [smartblade/BldMystery#7](https://github.com/smartblade/BldMystery/pull/7)
("Fix B_World class fields and offsets"), reviewed at commit `ee43e85`.

The procedures implemented in the pull request were converted by
BldRecompile (see `recompile/Blade.exe.cpp`) and compiled by Visual C++ 6.0
(`cl.exe` 12.00.8804 with `/Od /Ob1 /Zp4`, see `vc6check` in branch
`claude/vc6-compare`). The compiled code of each procedure was compared
with `Blade.exe` instruction by instruction. Each issue below comes with a
suggested patch against `ee43e85` or with suggested code.

Sections 1-5 are bugs, sections 6-12 are differences of the code generated
from the pull request from the original binary, section 13 reconstructs a
procedure called by the octree, section 14 is the code style which makes
the sources and the output of BldRecompile identical.

All suggestions are applied in branch `claude/pr7-styled` (based on
`ee43e85`). With them every procedure of the pull request, the scalar
deleting destructor of `B_OctantNodeBase` and
`B_SectorSurfaceCache::IsPointInside` compiled by Visual C++ 6.0 are
identical to `Blade.exe`, and the output of BldRecompile is identical to
the sources.

## 1. `~B_OctantNodeBase` is attributed to the scalar deleting destructor

`src/BWorld/OctTree.cpp` marks `0x00453AC0` as
`B_OctantNodeBase::~B_OctantNodeBase()` (`??1B_OctantNodeBase@@UAE@XZ`).
The code at this address is the compiler-generated scalar deleting
destructor of `B_OctantNodeBase`, not the destructor itself:

- it is the second entry of the `B_OctantNodeBase` vtable `g005BDD0C`,
  the slot of the virtual destructor;
- it takes the delete flag from `[ebp+8]`, calls `operator delete`
  (`l005BBD3D`) when bit 0 is set and returns with `ret 4`;
- the destructor body (`vtable = g005BDD0C; gbl_node_count--;`) is inlined
  into it, the destructor has no address of its own.

```asm
l00453AC0 PROC
           push ebp
           mov ebp, esp
           push ecx
           mov dword ptr [ebp-004h], ecx
           mov eax, dword ptr [ebp-004h]
           mov dword ptr [eax], offset g005BDD0C
           mov ecx, dword ptr [g005E338C]
           sub ecx, 000000001h
           mov dword ptr [g005E338C], ecx
           mov edx, dword ptr [ebp+008h]
           and edx, 000000001h
           test edx, edx
           je l00453AF5
           mov eax, dword ptr [ebp-004h]
           push eax
           call l005BBD3D
           add esp, 000000004h
l00453AF5: mov eax, dword ptr [ebp-004h]
           mov esp, ebp
           pop ebp
           ret 00004h
l00453AC0 ENDP
```

In the native build this is a bug: `procedures.inc` maps
`l00453AC0` to `??1B_OctantNodeBase@@UAE@XZ`, and the vtable still points
to `l00453AC0`. Deleting an octree node through a base class pointer
passes the delete flag, but the C++ destructor returns without popping it
(`ret` instead of `ret 4`) and never calls `operator delete`.

The constructor and the destructor of `B_OctantNodeBase` have no
addresses at all: their code (`vtable = g005BDD0C; gbl_node_count++;` and
`vtable = g005BDD0C; gbl_node_count--;`) is inlined into constructors and
destructors of `B_OctantNode`, `LeafNode` and `B_SectorListNode` and into
the scalar deleting destructor. With `/Ob1` Visual C++ inlines only inline
functions, so they are defined in the class in `OctTree.h`, not in
`OctTree.cpp`:

```cpp
class B_OctantNodeBase
{
public:
    B_OctantNodeBase()
    {
        gbl_node_count++;
    }

    virtual int GetTypeID() = 0;

    virtual ~B_OctantNodeBase()
    {
        gbl_node_count--;
    }

    ...

    /*
    *
    * Implicit definition of scalar deleting destructor.
    * Generated by compiler.
    *
    * Module:                 Blade.exe
    * Entry point:            0x00453AC0
    * VC++ mangling:          ??_GB_OctantNodeBase@@UAEPAXI@Z
    */
};
```

Suggested fix: define the constructor and the destructor in the class,
remove them from `OctTree.cpp` and map `0x00453AC0` to the scalar deleting
destructor generated by the compiler in `procedures.inc`:

```diff
--- a/src/Blade/asm/procedures.inc
+++ b/src/Blade/asm/procedures.inc
-externdef ??1B_OctantNodeBase@@UAE@XZ: near
-l00453AC0 equ ??1B_OctantNodeBase@@UAE@XZ
+externdef ??_GB_OctantNodeBase@@UAEPAXI@Z: near
+l00453AC0 equ ??_GB_OctantNodeBase@@UAEPAXI@Z
```

Compiled by Visual C++ 6.0, the generated `??_GB_OctantNodeBase@@UAEPAXI@Z`
is identical to `0x00453AC0`, and the constructors and destructors of
`B_OctantNode` (`0x00450327`, `0x00450380`) and `LeafNode` (`0x00450417`,
`0x00450450`) become identical to the binary too: with out of line
definitions they call the constructor and the destructor of
`B_OctantNodeBase` instead of inlining them.

## 5. `B_OctTreeSectorsList::BuildSurfaceCache` does not match the binary

The `// TODO double check` above `BuildSurfaceCache` (`0x0045327B`) is
justified. The code identical to the binary when compiled by Visual C++
6.0 is:

```cpp
int B_OctTreeSectorsList::BuildSurfaceCache(
    B_GlobalSurfaceCache *cache,
    const B_Sphere *sphere
)
{
    double distance;
    cache->count = 0;
    unsigned int i = 0;
    for (i = 0; i < this->size; i++)
    {
        B_Sector *current_sector = this->sectors[i];
        cache->elements[cache->count].sector = current_sector;
        cache->elements[cache->count].numSurfaces = 0;
        unsigned int j;
        for (j = 0; j < current_sector->size; j++)
        {
            B_Surface *current_surface = current_sector->elements[j];
            distance = current_surface->Distance(&sphere->center);
            if (-sphere->radius > distance)
            {
                j = current_sector->size + 1;
            }
            else if (distance < sphere->radius)
            {
                B_Surface *surface = current_sector->elements[j];
                cache->elements[cache->count].surfaces[cache->elements[cache->count].numSurfaces] =
                    surface;
                cache->elements[cache->count].numSurfaces++;
            }
        }
        if (j == current_sector->size)
        {
            if (cache->elements[cache->count].numSurfaces == 0)
            {
                cache->elements[cache->count].hasNoIntersections = 1;
                cache->count++;
                return 1;
            }
            cache->elements[cache->count].hasNoIntersections = 0;
            cache->count++;
        }
    }
    if (cache->count != 0)
    {
        return 0;
    }
    return -1;
}
```

Differences from the pull request:

1. If `-sphere->radius > distance` (the sphere is outside one of the
   planes), the inner loop is aborted with `j = current_sector->size + 1`
   and the sector is **not** added to the cache: `cache->count` is not
   incremented. The pull request always adds the sector.
2. A surface is added if `distance < sphere->radius` (strict), the pull
   request uses `distance <= sphere->radius`.
3. If the inner loop finished (`j == current_sector->size`) and no surfaces
   were added, the function sets `hasNoIntersections = 1`, increments
   `cache->count` and **returns 1 immediately**. The pull request has no
   early return.
4. There is no `cacheEntry` local variable, the code accesses
   `cache->elements[cache->count]` every time. Loop counters are
   `unsigned int`.
5. The added surface is read from `current_sector->elements[j]` again into
   another local variable (`surface`) instead of using `current_surface`.
6. `distance` is declared at the start of the procedure: it is placed at
   the top of the stack frame (`[ebp-008h]`), above `i` (`[ebp-00Ch]`).
   Visual C++ 6.0 places variables of the body of a procedure before
   variables of nested blocks (see `vc6check/stack-layout.md` in branch
   `claude/vc6-compare`), so it can't be declared in the loop.
7. The distance is calculated by an inline method of `B_Plane` (the parent
   of `B_Surface`), see below.

The assembler code of `0x0045327B` confirms it.

Abort of the inner loop (difference 1):

```asm
           mov eax, dword ptr [ebp+00Ch]      ; sphere
           fld qword ptr [eax+018h]           ; ST0 = sphere->radius
           fchs                               ; ST0 = -radius
           fcomp qword ptr [ebp-008h]         ; compare with distance
           fnstsw ax
           test ah, 041h                      ; C0|C3: -radius <= distance
           jne l0045336C                      ; yes -> check the surface
           mov ecx, dword ptr [ebp-010h]      ; no (distance < -radius):
           mov edx, dword ptr [ecx+008h]      ;   current_sector->size
           add edx, 000000001h
           mov dword ptr [ebp-014h], edx      ;   j = current_sector->size + 1
           jmp l004533DD                      ;   j++ and exit the loop
```

Strict comparison with the radius (difference 2):

```asm
l0045336C: mov eax, dword ptr [ebp+00Ch]
           fld qword ptr [ebp-008h]           ; ST0 = distance
           fcomp qword ptr [eax+018h]         ; compare with radius
           fnstsw ax
           test ah, 001h                      ; C0: distance < radius
           je l004533DD                       ; no -> skip the surface
```

The sector is added only if the inner loop finished, and the function
returns 1 if no surfaces were added (difference 3):

```asm

           mov ecx, dword ptr [ebp-014h]
```

## 8. `B_SectorListNode::CollectSectorsInBox` differs from `LeafNode::CollectSectorsInBox`

`B_SectorListNode::CollectSectorsInBox` (`0x00452232`) gives the same
result as in the pull request, but it is compiled the same way as
`LeafNode::CollectSectorsInBox` (`0x00452082`): there is no `queryBB`
local variable (`gbl_current_query_box` is read every time), the
intersection flag is computed with strict `>`/`<` comparisons, kept in a
local variable (`[ebp-008h]`) and then tested. The `<=`/`>=` comparisons of
the pull request are not the same as negated `>`/`<` comparisons for NaN
coordinates. Suggested code (identical to the binary when compiled by
Visual C++ 6.0):

```cpp
void B_SectorListNode::CollectSectorsInBox(
    const B_BoundingBox &, B_OctTreeSectorsList *outList,
    double
)
{
    for (unsigned int i = 0; i < this->size; i++)
    {
        if (
            this->elements[i]->lastQueryId != gbl_oct_tree_query_id &&
            this->elements[i]->isActive != 0
        )
        {
            this->elements[i]->lastQueryId = gbl_oct_tree_query_id;
            B_BoundingBox *sectorBB = &this->elements[i]->boundingBox;
            int intersects;
            if (
                gbl_current_query_box->minCoords.x > sectorBB->maxCoords.x ||
                gbl_current_query_box->minCoords.y > sectorBB->maxCoords.y ||
                gbl_current_query_box->minCoords.z > sectorBB->maxCoords.z ||
                gbl_current_query_box->maxCoords.x < sectorBB->minCoords.x ||
                gbl_current_query_box->maxCoords.y < sectorBB->minCoords.y ||
                gbl_current_query_box->maxCoords.z < sectorBB->minCoords.z
            )
            {
                intersects = 0;
            }
            else
            {
                intersects = 1;
            }
            if (intersects != 0 && outList->size < 512)
            {
                outList->sectors[outList->size] = this->elements[i];
                outList->size++;
            }
        }
    }
}
```


  The element is a separate local variable: with
  `outBuffer.Append(sectors.elements[i])` Visual C++ 6.0 puts the argument
  of the inlined `Append` to another place in the stack frame. With
  `int Intersects` (section 2) the procedure is identical to the binary.

- Parameters of `LeafNode::CollectSectorsInBox` and
  `B_SectorListNode::CollectSectorsInBox` have no names:
  `(const B_BoundingBox&, B_OctTreeSectorsList* outList, double)`. They
  aren't used, so they stay unnamed (BldRecompile writes a parameter
  without a name when it's named `__` in characteristics).

## 10. Octree constants are literals, not `static double` variables

`src/BWorld/OctTree.cpp` declares

```cpp
static double child_size_divisor = 2.0;
static double child_offset_divisor = 4.0;
static double kOctTreeMargin = 10.0;
```

and compares coordinates with `kOctTreeMargin` and `-kOctTreeMargin`. In
the binary the values are read from `.rdata` (`005BD000`-`005C7072`),
which is not writable, while non-const `static double` variables would be
placed to `.data` (`005C8000`). `-kOctTreeMargin` is not computed with
`fchs` either, it is a separate constant `-10.0`:

| Address | Value |
|---|---|
| `0x005BD710` | `2.0` |
| `0x005BDB68` | `4.0` |
| `0x005BDB88` | `10.0` |
| `0x005BDD48` | `-10.0` |

```asm
l00452388 PROC                          ; B_OctantNode::CollectSectorsAtPoint
           ...
           fld qword ptr [ebp+010h]     ; halfSize
           fdiv qword ptr [g005BD710]   ; / 2.0
           fstp qword ptr [ebp-008h]
           fld qword ptr [ebp+010h]     ; halfSize
           fdiv qword ptr [g005BDB68]   ; / 4.0
           fstp qword ptr [ebp-010h]
           ...
           fld qword ptr [eax]          ; localPos.x
           fcomp qword ptr [g005BDB88]  ; < 10.0
           ...
           fcomp qword ptr [g005BDD48]  ; > -10.0
```

The converted code (`B_OctantNode::CollectSectorsAtPoint`,
`B_OctantNode::CollectSectorsInBox`, `B_OctTree::FindSectorsAtPoint`):

```cpp
STACKVAR(-8, 8) = halfSize / 2.0;
STACKVAR(-16, 8) = halfSize / 4.0;
if (localPos.x < 10.0)
...
            if (localPos.z > -10.0 && ACCESS(this, 8, 4) != 0x00000000)
...
if (this->m_root != nullptr && this->m_halfSize + 10.0 > fabs(reinterpret_cast<double>(STACKVAR(-24, 8))) && ...)
```

So the original code used literals (`2.0`, `4.0`, `10.0`, `-10.0`). With
the `static double` variables of the pull request the compiler reads them
from `.data` and computes `-kOctTreeMargin` with `fld` and `fchs`. With
`static const double` constants Visual C++ 6.0 still reads the variables:
in `B_OctTree::FindSectorsAtPoint` it loads the constant before
`this->m_halfSize` in `this->m_halfSize + kOctTreeMargin`, the binary loads
the field first and adds the constant, like for a literal. Suggested fix:
keep the names as macros of literals:

```cpp
#define child_size_divisor 2.0
#define child_offset_divisor 4.0
#define kOctTreeMargin 10.0
```

With them `B_OctTree::FindSectorsAtPoint` is identical to the binary.

## 11. `B_SectorListNode` is derived from `B_PtrArray` directly

The constructor of `B_SectorListNode` (`0x0045048C`) assigns the fields of
the array of sectors and then the only table of virtual methods of the
array (`g005BDB7C`, the table of `B_PtrArray`):

```asm
           mov edx, dword ptr [ebp-008h]
           add edx, 000000004h
           mov dword ptr [ebp-004h], edx
           mov eax, dword ptr [ebp-004h]
           mov dword ptr [eax+004h], 000000000h   ; elements = NULL
           mov ecx, dword ptr [ebp-004h]
           mov dword ptr [ecx+008h], 000000000h   ; size = 0
           mov edx, dword ptr [ebp-004h]
           mov dword ptr [edx+00Ch], 000000001h   ; increment = 1
           mov eax, dword ptr [ebp-004h]
           mov dword ptr [eax+010h], 000000000h   ; num_alloc = 0
           mov ecx, dword ptr [ebp-004h]
           mov dword ptr [ecx+014h], 000000001h   ; deleteItems = 1
           mov edx, dword ptr [ebp-004h]
           mov dword ptr [edx], offset g005BDB7C  ; B_PtrArray vtable
```

The destructor (`0x0045050B`) clears the array without deletion of
sectors on the subobject `this + 4` itself (without a check for null and
without a table of an intermediate class), then the inlined destructor of
`B_PtrArray` follows (with its table `g005BDB7C` and
`Clear(deleteItems)`, which does nothing because the array is empty), then
the destructor of `B_OctantNodeBase`. There is no `B_SharedPtrArray` between
`B_SectorListNode` and `B_PtrArray`: the node doesn't own the sectors of
the map, its destructor clears the array before the destructor of
`B_PtrArray` would delete them.

All inlined constructors of `B_PtrArray` in the binary assign the fields
before the table and use constant arguments directly: the fields are
initialized in the initializer list, and the increment is `int` like the
field (Visual C++ 6.0 copies an `unsigned int` argument converted to `int`
to a temporary).

```cpp
class B_SectorListNode : public B_OctantNodeBase, public B_PtrArray<B_Sector>
...

B_SectorListNode::B_SectorListNode()
:
    B_PtrArray<B_Sector>(1)
{
}

B_SectorListNode::~B_SectorListNode()
{
    this->Clear(false);
}
```

```cpp
template<class TYPE>
class B_PtrArray
{
public:
    ...
    B_PtrArray(int increment = 16, int deleteItems = true)
    :
        elements(NULL),
        size(0),
        increment(increment),
        num_alloc(0),
        deleteItems(deleteItems)
    {
    }
    ...
};
```

With them the constructor and the destructor of `B_SectorListNode` are
identical to the binary. The new constructor of `B_PtrArray` makes other
implemented procedures closer to the binary too (`B_App::B_App`,
`B_App::ReadArguments`, `CreateTriggerSector`, `LoadCombustionData`,
`GetEnemiesVisibleFrom`), no procedure becomes worse.

## 12. Temporaries and names of local variables of `B_OctantNode`

`B_OctantNode::CollectSectorsAtPoint` (`0x00452388`) has no local vectors:
its stack frame (`0x194` bytes) consists of `this`, two `double` variables
and 8 pairs of temporary vectors of 24 bytes (the center of a child and the
position relative to it). The children are called with temporaries:

```cpp
this->children[0]->CollectSectorsAtPoint(
    localPos - B_Vector(-childCenterOffset, -childCenterOffset, -childCenterOffset),
    outList,
    childHalfSize
);
```

Visual C++ 6.0 orders the variables of a block in the stack frame by the
hash of their names, not by the order of declarations (see
`vc6check/stack-layout.md` in branch `claude/vc6-compare`). The names of
the pull request give an order different from the binary:

| Procedure | Variable | Binary | Pull request | Suggested |
|---|---|---|---|---|
| `CollectSectorsAtPoint`, `CollectSectorsInBox` | `halfSize / 2.0` | above | `childHalfSize` | `childHalfSize` |
| `CollectSectorsAtPoint`, `CollectSectorsInBox` | `halfSize / 4.0` | below | `childOffset` | `childCenterOffset` |
| `CollectSectorsInBox` | box of children | top | `childBox` | `childBoundingBox` |

With the temporaries and the suggested names both procedures are
identical to the binary.

## 13. `B_SectorSurfaceCache::IsPointInside`

`IsPointInside` declared in `OctTree.h` is at `0x004534A4`, right after
the destructor of `B_SectorSurfaceCache`. It is called once
(`0x00499AA2`) for an element of an array of 272 bytes (the size of
`B_SectorSurfaceCache`) with a pointer to a vector, its result is tested
as a boolean. It checks the distance from the point to the surfaces of the
cache with the inlined `B_Plane::Distance` (section 5), `0.0` is the
literal `g005BD728`:

```cpp
/*
* Module:                 Blade.exe
* Entry point:            0x004534A4
* VC++ mangling:          ?IsPointInside@B_SectorSurfaceCache@@QAEHPBVB_Vector@@@Z
*/

int B_SectorSurfaceCache::IsPointInside(const B_Vector *point)
{
    for (unsigned int i = 0; i < this->numSurfaces; i++)
    {
        if (this->surfaces[i]->Distance(point) < 0.0)
        {
            return 0;
        }
    }
    return 1;
}
```

Compiled by Visual C++ 6.0 it is identical to the binary.

## 14. Code style

The goal is that the implemented procedures are identical to the output of
BldRecompile. The compiler doesn't keep the differences below, so the style
of BldRecompile output is used:

1. `&` and `*` are attached to names, not to types:
   `const B_Vector &that`, `B_Sector *sector`.
2. Opening braces are on separate lines, there is no `;` after the closing
   brace of a function:

   ```cpp
   int B_SectorListNode::GetTypeID()
   {
       return B_OCT_NODE_CID_SECTOR_LIST;
   }
   ```

3. Loop counters are incremented with postfix `i++`, not `++i`.
4. Fields and methods are accessed with explicit `this->`:
   `this->children[i] = nullptr;`.
5. Nested `if` statements without `else` are merged with `&&`:
   `if (bb.minCoords.z < 10.0 && this->children[0] != nullptr)` instead of
   `if (bb.minCoords.z < 10.0) { if (children[0]) { ... } }`.
6. Integer literals are decimal: `outList->size < 512`, not `0x200`.
7. There are no comments and no commented out code inside procedures,
   e.g. `// mark as "processed"`, `// TODO double check` and the commented
   out implementation of `B_Vector::operator -`.
8. Lines longer than 80 characters are wrapped the way BldRecompile does
   it when it updates sources (`process_asm.py --update-src-at`):

   ```cpp
   void B_OctantNode::CollectSectorsInBox(
       const B_BoundingBox &bb,
       B_OctTreeSectorsList *outList,
       double halfSize
   )
   {
       ...
           if (
               bb.maxCoords.z > -kOctTreeMargin &&
               this->children[1] != nullptr
           )
   ```

9. Procedures of a source file are in the order of their addresses: Visual
   C++ 6 places procedures of a file in the order of their definitions. In
   `OctTree.cpp` `B_SectorSurfaceCache::~B_SectorSurfaceCache` (0x00453490)
   must be defined before `B_GlobalSurfaceCache::B_GlobalSurfaceCache`
   (0x004539A9). BldRecompile can't update sources with procedures in other
   order.
10. There are no blank lines inside procedures, including empty bodies and
    lines before `return`:

    ```cpp
    B_SectorListNode::~B_SectorListNode()
    {
    }

    int B_OctantNode::GetTypeID()
    {
        return B_OCT_NODE_CID_BRANCH;
    }
    ```
11. Initializer lists start with `:` on a separate line, each initializer
    is on its own line:

    ```cpp
    B_SectorListNode::B_SectorListNode()
    :
        B_PtrArray<B_Sector>(1)
    {
    }

    B_BoundingBox::B_BoundingBox(
        const B_Vector &minCoords,
        const B_Vector &maxCoords
    )
    :
        minCoords(minCoords),
        maxCoords(maxCoords)
    {
    }
    ```
12. Elements of arrays are accessed directly, not with inline methods:
    `this->elements[i]` instead of `(*this)[i]`. Inline methods are
    compiled into the same code, BldRecompile can't restore them.
13. Pointers are compared with `nullptr` explicitly:
    `this->children[0] != nullptr` instead of `this->children[0]`.
14. Local variables are declared without `const`:
    `double childHalfSize = halfSize / child_size_divisor;`.
    Names of local variables keep the order of the variables in the stack
    frame of the binary (section 12).
15. Fields assigned at the start of a constructor are initialized in the
    initializer list, also for classes without virtual methods:

    ```cpp
    B_OctTreeSectorsList::B_OctTreeSectorsList()
    :
        size(0)
    {
    }
    ```
